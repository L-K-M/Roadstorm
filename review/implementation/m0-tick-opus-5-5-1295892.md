## Findings (ranked)

### F1 — Major: `begin_step()` from a physics callback after the coordinator lets one physics-server step run with zero logical ticks

`tools/tick_probe/src/tick_coordinator.gd:289-290`, together with `:383` and `src/pause_enforcer.gd:17`.

`begin_step()` unpauses the tree synchronously (`set_frozen(false)`). The coordinator's own design depends on this Godot 4 rule: `SceneTree.paused` toggles `PhysicsServer3D` activity, and that iteration's server `step()` runs after all `_physics_process` callbacks. Its comments say so ("pausing inside the physics callback would suppress that step").

The mirror case is not handled. Suppose a node processed *after* the coordinator calls `begin_step()` from its `_physics_process`, for example:

- a training bridge or motor-facing node,
- any later sibling,
- a node with a higher `process_physics_priority`.

In that iteration the coordinator has already returned at `:383`, because `_budget` was 0. The tree is unpaused when the server steps, so the world integrates one step with no logical tick, no RNG draw and no event.

The consequences:

- A 12-tick request yields 13 server steps. Dynamic bodies, contacts and areas advance while the coordinator is "waiting".
- This breaks "zero advancement while waiting" and "only it advances clocks, RNG, contacts" (TECHNICAL_DESIGN.md:65).
- The probe car itself is unaffected, because it only moves through explicit `move_and_collide`. That is why the kinematic-only fidelity traces cannot see the problem.

Nothing guards, documents or tests this. Every `begin_step` call site in `src/` and `tests/` (git grep) runs from a coroutine resumed on `process_frame`, i.e. idle time.

**Fix:** make unpausing an iteration-boundary action. Two options:

1. `begin_step()` only arms the budget and keeps the tree paused. The `PROCESS_MODE_ALWAYS` enforcer, at the lowest `process_physics_priority`, unpauses at the start of the next physics iteration.
2. When `Engine.is_in_physics_frame()` and the coordinator has already processed the current `Engine.get_physics_frames()`, keep the tree paused until the next iteration.

**Test to add:** a contract test that calls `begin_step(12)` from a `_physics_process` ordered after the coordinator, using a *warmed* counting body, and requires `server_steps_delta == 12`. Confidence is high from engine-loop semantics and the candidate's own pause rationale, but I could not execute it.

### F2 — Medium: the N1 request gate was weakened to `>=`, which, combined with fresh-body registration, can hide exactly the F1 defect class

`tools/tick_probe/tests/n1_regression_driver.gd:132`.

The check changed from `pf_delta == n + 1` to `pf_delta >= n + 1`.

`pf_delta` is now sampled inside the `step_finished` handler (`signal_engine_pf`). That makes it deterministic: one physics iteration per tick plus the single pause iteration. Catch-up does not change iteration indices.

- Every committed sample shows exactly `n + 1` (`cold-control/post-fix-n1-max.txt`: 2, 13, 25, 13, 13).
- README.md:190-192 still documents `engine_pf_delta = n + 1`.

Why `>=` matters:

- `>=` accepts an extra unpaused iteration before the first tick.
- All exact-step request scenarios use a *freshly spawned* body (`_spawn()` in `_request_scenario`).
- The cold-control evidence shows that a fresh body can absorb the first unpaused server step as registration (cold diagnostic: k=1 gives 0 at fixed/default).

So an untracked leading server step, as in F1, can pass *both* the `>=` check and `server_steps_delta == n`.

**Fix:**

- Restore exact equality, now that signal-time sampling has removed the poll-timing flake.
- Add the same request checks on a warmed body, as `_warmed_continuous_control` already does for the instrument.
- Keep the fresh-body cases as well.

### F3 — Medium (plausible, not executed): the motion-bound "no server step" check probably cannot detect a one-step leak

`tools/tick_probe/tests/contract_driver.gd:95-106` with `_spawn_counting_body()` at `:486`.

The refusal path pauses inside the first physics callback *before* any space query (`tick_coordinator.gd:393-398`). The test asserts `dyn.server_steps == 0` on a body spawned cold just before the request.

The candidate's own cold-control evidence says a cold body without an intervening query does not integrate its first unpaused step at fixed or default pacing. A mutation that deferred the motion-bound pause by one iteration would therefore probably still read 0.

The exact request scenarios apparently avoid this because the coordinator's per-tick `cast_motion`/`test_move`/`move_and_collide`/`intersect_ray` flush the pending Jolt registration before the step. That is my inference from cold k=1 → 0 versus `single_1` → 1. The refusal path issues no query.

**Fix:**

- Warm the counting body (as in `_warmed_continuous_control`) before `reset()`/request.
- Record a mutation run (motion-bound with `defer_pause = true`) that must fail.

### F4 — Minor: the pause enforcer does not change the measured F1 exposure, and the prior-node exposure stays open for motor integration

- `pause_enforcer.gd`
- `tick_coordinator.gd:312-318`
- evidence `callback-ordering/f1f3-pre-c6292a2.txt` and `f1f3-post-fix.txt`

The pre-fix and post-fix F1/F3 outputs are byte-identical (same manifest hash `7ef30b4e...`; I confirmed identical content by reading both). In each, the node before the coordinator gets 13 callbacks and the node after it gets 12.

The enforcer is a child of the coordinator, so it runs directly after the coordinator, which already pauses at the same point. It adds machinery without changing behaviour.

Setting the enforcer's `process_physics_priority` to the minimum would make it pause before *all* default-priority nodes. That closes the documented "nodes before the coordinator see an extra callback" exposure instead of handing it to M1. It also combines naturally with the F1 fix.

If you keep the current design, the motor integration task must explicitly require all simulation work to run inside the coordinator tick, with no independent `_physics_process`.

### F5 — Minor: the enforcer fallback fails open if the enforcer is freed

`tick_coordinator.gd:377-380` only falls back to `request_deferred_pause()` when `_pause_enforcer == null`.

If the helper is freed externally, the reference is non-null but invalid. Neither path then pauses, so the tree stays unpaused with `_emit_scheduled == true`: no result is ever published and the world keeps server-stepping.

**Fix:** use `not is_instance_valid(_pause_enforcer)`.

Relatedly, `configure()` (`:141-153`) ends with the tree **unpaused** and is only safe because every caller follows it with `reset()`. Freeze at the end of `configure()` to keep the "frozen whenever waiting" invariant self-contained.

### F6 — Minor: the strict result parsers still have gaps

`tests/run_contract_tests.py:104-132` and `tests/run_n1_tests.py:83-109`.

- `--expect-checks` defaults to 0 (disabled). A run that silently skips test coroutines, or reports `checks_total: 0`, passes when the remaining checks pass.
- `checks_failed` is not reconciled with `len(failures)` or with the printed `TESTS_FAILED=` / `N1_FAILED=` line.
- `TESTS_TOTAL` uses the first regex match, while `TEST_RESULT` uses the last line.

The new fail-closed rule (`failed != 0` gives exit 1) is correct, and the injected-failure double is a good control.

**Fix:**

- Require a positive pinned count, or bake in a default.
- Cross-check failures against `checks_failed`.
- Take the last occurrence of both lines.
