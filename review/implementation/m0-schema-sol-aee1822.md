## Ranked findings

1. **High · TacticalIntent accepts invalid speed decoding and safety telemetry.** In [tactical_intent.schema.json](../../schemas/intent/tactical_intent.schema.json#L146), the pace interval endpoints are independently non-negative and the decoded target has no relationship to the interval or normalized action. [The checker](../../fixtures/intent/validate_intent_contract.py#L576) validates lateral decoding only. [The correction shape](../../schemas/intent/tactical_intent.schema.json#L393) permits negative speeds, and [its semantic check](../../fixtures/intent/validate_intent_contract.py#L828) only compares the declared material flag to the numbers in the correction. A rehashed Surge example with an inverted interval (min 60, max 20), a 90 m/s target and a road correction from 20 to −10 m/s passed both validators. Enforce ordered intervals, verify the decoded speed against the normalized action when the interval is known, and check speed corrections against that pre-safety decode with nonnegative values. This uses synthetic numbers and leaves M4.3 interval tuning open. [Action contract](../../docs/OPPONENT_AI.md#L55) · [Safety accounting](../../docs/BENCHMARKS.md#L70)

2. **High · The observation-to-intent link has no consistency gate.** [The intent schema](../../schemas/intent/tactical_intent.schema.json#L50) describes `source_observation_id` as its source record, and [the validator pipeline](../../fixtures/intent/validate_intent_contract.py#L1173) never loads observations. I replaced the first Surge source with the existing `obs.t001008.ai_surge_2`, which belongs to a different participant and tick. Both validators accepted the rehashed document. The three resolvable shipped links match participant, tick, difficulty, style, delayed traffic age, frame, reset generation, and the example road widths. The two missing follow-on IDs are already disclosed. Add an integration check for resolvable and unique fixture sources and their shared fields. Supply the two missing examples or explicitly model the exception so a broken reference is distinguishable from an intentional illustration. [Current fixture reference disclosure](../../fixtures/intent/README.md#L102)

3. **Medium · A raw-input key alias bypasses the enforced 70 m neighbor window.** [Window checking](../../fixtures/observation/validate_observation_contract.py#L728) looks up `str(gap_idx)` and falls back to the clipped feature if absent. [Normalization checking](../../fixtures/observation/validate_observation_contract.py#L998) converts keys with `int(key)`. With one present neighbor, a clipped gap of 1.0 and a raw input of `"027": 80`, the rehashed fixture passed the observation validator. The checker uses 70 m from the clipped vector for eligibility and simultaneously accepts the authoritative 80 m input as internally consistent. Require canonical index strings or normalize keys once and reject duplicate indices. [Documented route window](../../docs/OPPONENT_AI.md#L49)

4. **Medium · Safety accounting cannot be reconstructed from the declared intent correction shape.** [Safety](../../schemas/intent/tactical_intent.schema.json#L245) describes one correction entry per corrected field, and [a correction](../../schemas/intent/tactical_intent.schema.json#L393) has no tick, exposure, separate emergency replacement, or reset event. [Scenario telemetry](../../schemas/scenario/scenario.schema.json#L525) requests safety corrections without identifying a companion event payload. Thus an intent corrected once and one corrected on multiple 60 Hz ticks can yield the same record, and the declared correction categories cannot identify emergency substitution. Define where tick-linked intervention events and replacement/reset evidence live, keeping the proposed intent identity for 5 Hz deduplication. Actual intervention counts and performance belong to later measured runs. [Benchmark counting protocol](../../docs/BENCHMARKS.md#L70) · [Separate intervention categories](../../docs/OPPONENT_AI.md#L132)

5. **Medium · Reference evidence drops two required content hashes.** [The closed reference hash object](../../schemas/scenario/reference_run.schema.json#L211) permits car, loadout and assist hashes only. [The schema description](../../schemas/scenario/reference_run.schema.json#L4) treats the benchmark’s course/handling revision requirement as conflicting with the track/handling hashes in Technical Design. The requirements can be represented together. Preserve both revisions and hashes, using explicit unknowns for planned artifacts, or record an authorized change to the design requirement. [Benchmark reference dependencies](../../docs/BENCHMARKS.md#L9) · [Technical Design content contracts](../../docs/TECHNICAL_DESIGN.md#L109)

6. **Medium · The coefficient revision can misidentify the normalization used.** [The revision field](../../schemas/observation/observation_record.schema.json#L150) accepts any nonempty string, and [normalization checks](../../fixtures/observation/validate_observation_contract.py#L998) use the embedded layout constants regardless of that string. Replacing the current example slug with `foreign_v99` passed with the original vector and raw probes. The contract should bind its known coefficient set to a revision or define the registry that selects the correct coefficients. The listed coefficient values and feature layout are provisional. [Revision and fallback requirements](../../docs/OPPONENT_AI.md#L49)

7. **Low · JSON Schema agreement is narrower than the integration summary.** A rehashed intent with `generated_tick: 996.0` instead of `996` passed Ajv and failed the [Python type check](../../fixtures/intent/validate_intent_contract.py#L234). JSON Schema integer uses the numeric value, while Python distinguishes the parsed numeric type here. Align the checker or explicitly document a tighter serialization profile and its hash handling. The five metric-shape differences already documented in [schemas/README.md](../../schemas/README.md#L105) reject the same files on both paths. Two editorial corrections are also due. The positive fixtures are provisional or illustrative and [PLAN.md](../../PLAN.md#L93) places schema ratification in M2.7, while [the integration record](../../schemas/README.md#L19) and [intent schema](../../schemas/intent/tactical_intent.schema.json#L39) use ratified/accepted wording. The [hash summary](../../schemas/README.md#L122) lists two intentionally bad hashes, but the independent count found three.
