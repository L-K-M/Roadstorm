## Findings (ranked)

### F1 — High: the intent contract cannot record a held pass commitment, the 0.4 s minimum commitment is unenforced, and proposed and executed labels are conflated

- `schemas/intent/tactical_intent.schema.json:186-193`: `commitment.label` is described as
  the pure threshold decode of `commitment_raw` (below −1/3 follow, from −1/3 to +1/3 wait,
  above +1/3 commit). `min_commitment_s` is only `const: 0.4`.
- `fixtures/intent/validate_intent_contract.py:669-690` (`check_label_thresholds`) requires
  `label == threshold(commitment_raw)` for every record.
  `fixtures/intent/validate_intent_contract.py:863-879` (`check_min_commitment`) only
  checks that the constant equals 0.4. No check spans records.
- OPPONENT_AI.md:61 says "commit to a legal pass; minimum commitment 0.4 s, interrupted by
  hazards". OPPONENT_AI.md:64 says "Classic planners emit this same intent, including
  continuous proposed values **and decoded/executed labels** … Record the proposed intent,
  ordinary difficulty decoding, safety changes and final commands separately."
- **Repro:** in `fixtures/intent/positive/fixture.intent.surge_commit_pass.json`, record 1
  (tick 1008) is 0.2 s after the commit at tick 996. Its own note says "the commitment
  cannot lapse yet". Set that record's `commitment_raw` to `0.0`, which is a legal
  policy output.
  - Keeping `label: "commit_pass"`, which is what the 0.4 s rule requires, makes
    `label_thresholds` reject it. The contract cannot represent correct behavior.
  - Setting `label: "wait"` passes every check, although the record now shows the
    commitment lapsing after 0.2 s, which breaks the 0.4 s minimum.

  The shipped fixture avoids this case only because it holds `commitment_raw` at 0.5.
- `drift.label` has the same problem (schema `:218-221`). `retain` records the decode
  band, not the preference actually retained, so the executed drift or grip preference
  cannot be recovered from a record. The post-reset fixture (`fixture.intent.post_reset_defaults.json:72-76`)
  already has to explain that "retain" means nothing there.
- **Impact:** demonstration and telemetry records lose the executed commitment and drift
  state. BENCHMARKS.md:66 labels "commit within 0.6 seconds versus wait" and
  "drift-entry timing category" from these records. Fixing this later changes the
  record shape and needs a new `schema_version`.
- **Fix:** split the proposed decode from the executed state. For example, keep `label` as
  the threshold decode and add `executed_label` (`follow|wait|commit_pass`) plus
  `commit_started_tick`. Add `drift.executed_preference` (`drift|grip|none`). Add a
  cross-record check that an executed `commit_pass` is held for at least 24 ticks unless
  `interrupted` is true. Add negative fixtures for an early lapse and for a held commit
  that is mislabeled.

### F2 — High: in a tactical scenario, every matched driver is a simultaneous participant at the identical pose

- `schemas/scenario/scenario.schema.json:142-148`: `participants` are "Cars taking part, at
  most the standard eight-car field". The `matched_*` roles at `:310-320` are ordinary
  participants. No member expresses alternative runs that put each evaluated driver into
  the same slot.
- `:175-179` and `:399`: the validator requires an entry in `per_participant_state` for
  every `matched_*` participant, and "Matched participants … carry the same values".
- `fixtures/scenario/positive/fixture.scenario.tactical_window_slower_lead.json` (the
  participants array, and `per_participant_state` from about line 112): `classic`,
  `cloning`, `surge` and `switch` all have `forward_gap_m 10`, `lateral_offset_m 0`,
  `speed_m_s 30` and `heading_offset_deg 0` in one five-car scenario. Read literally,
  four cars occupy the same position at the window start.
- BENCHMARKS.md:64 says "Compare Classic, cloning-only, Surge, and Switch from matched
  initial states and histories". That describes separate matched runs, in which each
  evaluated driver faces the same lead and traffic. Running them together makes each
  car traffic for the others, so their histories cannot match. It also means
  contact/depenetration at t=0.
- **Impact:** the scenario contract cannot represent the BENCHMARKS tactical protocol
  coherently, and the shipped example encodes co-located cars. This shape would carry
  into every one of the six families.
- **Fix:** model one evaluated slot plus fixed context participants, and list the compared
  producers as `arms`/`variants` (each a driver spec) that run in separate executions
  with the same seed, initial state and history. Alternatively, keep one scenario per
  arm and add a shared `comparison_group_id`. Add a validator rule that no two
  simultaneous participants share a pose.

### F3 — Medium-high: the observation slice accepts metric shapes that the shared schema rejects

- The observation slice's subset evaluator
  (`fixtures/observation/validate_observation_contract.py:283-300`, "Supported keywords …")
  ignores `allOf`/`if`/`then`. Its only metric check, `check_comparison_metrics`
  (`:1164-1186`), rejects only `status: "measured"`. Unlike the intent (`:921`), scenario
  (`:1245`) and handling (`:930-962`) validators, it has no `metric_shape` check.
  `schemas/observation/observation_fixture.schema.json:153-168` also leaves
  `metric_shape` and `metric_status_honesty` out of the expectation `check` enum, and its
  path pattern (`:173`) allows only `records…`.
- `schemas/common.schema.json:105-135` (`acceptance_metric.allOf`) forbids `value` on
  `report` and on `range`/`ratio_range`, and requires bounds on range comparators.
- `schemas/README.md:105-115` says "each slice therefore re-implements the identical rules
  semantically as its `metric_shape` check … Both layers reject them, so no defect is
  missed". That is false for the observation slice.
- **Repro (not executed):** copy
  `fixtures/observation/positive/fixture.observation.surge_full_vector.json` to a scratch
  directory. In `comparison.metrics[0]`, replace `"comparator": "lte", "value": 0.5` with
  `"comparator": "ratio_range"` and add no bounds. Recompute `content_hash` with the
  validator's hash-update path, or with the canonical-JSON rule in
  `common.schema.json:20`. Then validate:
  - `validate_observation_contract.py` reports no failure: there is no `allOf`, no
    `metric_shape`, and the status is not `measured`.
  - Any draft 2020-12 validator, such as the README's Ajv run, rejects it under the
    `allOf[1]` clause (required `value_min`/`value_max`).
- **Impact:** the "both layers reject" guarantee does not hold for the observation slice.
  A malformed acceptance target in an observation fixture is accepted by the shipped
  checker.
- **Fix:** port `check_metric_shape` (and `metric_status_honesty`) into the observation
  validator, extend the expectation enum and path pattern, add
  `bad_metric_*` negatives to `fixtures/observation/negative/`, and correct
  `schemas/README.md:105-115`.

### F4 — Medium: the observation lane normalization and the intent lateral normalization use different, unratified half-widths

- OPPONENT_AI.md:41 sets index 4 as "lane offset/usable half-width". OPPONENT_AI.md:44
  divides history lane targets 51–52 "by its then-usable half-width". OPPONENT_AI.md:59
  decodes action 0 with `(road_width - car_width)/2 - 0.5 m`.
- The fixtures set "usable half-width" to `road_width/2`: 10 m gives 5.0
  (`fixture.observation.classic_rookie_clear.json:20`), and 12 m gives 6.0
  (`fixture.observation.surge_full_vector.json:20`; `schemas/README.md:33-35` calls this
  "the same convention"). The intent corridor for the same 12 m section is 4.6 m
  (`fixture.intent.surge_commit_pass.json`).
- `observation_fixture.schema.json:89-93` calls `usable_half_width_m` an "authored
  illustrative value". It defines no formula, and no fixture `unknowns` entry flags it.
- **Consequence:** a car at the legal corridor edge has observation feature 4 =
  4.6/6.0 ≈ 0.77, while its intent `lateral_target_norm` = 1.0. The recorded "own
  executed normalized lane target" (51–52) and the intent's normalized target live on
  different scales, and the contract does not say which one history stores.
  A learned policy trains against whichever convention the builder happens to use.
  Changing it after the freeze is a layout revision.
- **Fix:** define `usable_half_width_m` explicitly, either as the action-0 legal corridor
  or as `road_width/2`. Then state whether features 51–52 store `decoded_offset_m /
  usable_half_width` or `lateral_target_norm`, and add a cross-slice check. Until that
  is decided, list it as a blocking unknown in the observation and intent fixtures.

### F5 — Medium: intent-to-observation references are never resolved, so the cross-slice drift fixed by hand in this commit can recur

- `tactical_intent.schema.json:50-54`: `source_observation_id` "ID of the observation
  record this intent was computed from".
- The intent validator never loads the observation fixtures. `check_context_agreement`
  (`validate_intent_contract.py:546-573`) compares records only with their own context.
- `schemas/README.md:28-51` (decisions 1–3) records that the road width disagreed with the
  referenced observation in two positive fixtures and 18 negative copies. All of them
  were found and fixed by hand.
- **Repro (static):** in `fixture.intent.post_reset_defaults.json`, change
  `context.road_width_m` back to 12.0 and the corridor to 4.6 m. The intent validator
  still passes, because all of its checks are internal. The referenced
  `obs.t000800.ai_classic_4` still encodes a 10 m road. The same holds for
  `traffic_age_ticks`, `difficulty`, `style`, `participant_id`, `reset_generation` and
  `history_valid`.
- **Fix:** add an optional cross-slice check. When `source_observation_id` resolves to a
  shipped observation record, require agreement on participant, difficulty, style,
  traffic age, reset generation and `history_valid`, require `generated_tick ≥` the
  observation's `sampled_tick`, and require the road width to match index 14 × 20 m.
  Report IDs that do not resolve as declared-illustrative, as the fixtures' prose
  already does.

### F6 — Medium: emergency replacement and persistent Classic substitution cannot be recorded, although two acceptance gates count them

- OPPONENT_AI.md:125 requires "Emergency replacements <1%", and OPPONENT_AI.md:132 says
  "emergency substitution/reset is separate". BENCHMARKS.md:70 says to count "emergency
  replacements and material road/collision corrections per proposed 5 Hz intent", and
  BENCHMARKS.md:56 says "persistent replacement by Classic counts as a learned failure".
- `tactical_intent.schema.json:393-420`: `correction.field` allows only lateral and pace,
  and `category` allows only `road|passing_room|contact_rule|physical_capability`. The
  object has `additionalProperties: false`, and no record member marks an emergency
  substitution or a Classic fallback. The scenario `required_telemetry` enum
  (`scenario.schema.json:233-255`) has no emergency or fallback channel either.
- This is partly acknowledged: `fixtures/intent/README.md:62-63` lists "how a safe
  fallback intent is represented" as not represented. The emergency-replacement half of
  the safety-interventions metric is not listed.
- **Fix:** add `safety.emergency` (for example `{substituted: bool, kind:
  "emergency_stop|reset|classic_fallback", ticks}`) or an equivalent telemetry channel
  before the freeze, or list it as a blocking unknown so that the freeze does not close
  over it.

### F7 — Low: the neighbor tie-break rule cannot be checked

OPPONENT_AI.md:49 says neighbors are "sorted by absolute gap then stable participant ID".
Observation records carry no neighbor participant IDs, and `check_neighbor_ordering`
(`validate_observation_contract.py:702-725`) checks only that `|gap|` is non-decreasing.
Two neighbors with equal |gap| (for example +35 m and −35 m, both 0.5) can appear in
either order. This matters for GDScript/Python parity, because slot order changes the
actor input. **Fix:** add an optional `neighbor_ids` array, which is diagnostic only and
stays out of the feature vector, and check the tie order.

### F8 — Low: the subset evaluators type JSON `1.0` as non-integer

`_json_type` (`validate_observation_contract.py:230-245`, and the same code in the other
validators) maps a Python `float` to `"number"`. A tick such as `"sampled_tick": 500.0` is
therefore rejected by the slice, while draft 2020-12 and Ajv accept it as an integer. This
is a stricter divergence and lets no defect through, but it contradicts the claim that the
slices and Ajv agree. **Fix:** treat floats with `is_integer()` as integers, or document the
stricter rule.
