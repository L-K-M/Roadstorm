## Ranked implementation finding

1. **Medium, blocking — Numeric exponent decoding can silently bypass authored-value checks.** The scanner validates exponent syntax only (`src/course/road_source.gd:688–719`), then `parse_json` hands the original number to Godot and uses its decoded value (`:1140–1153`). In the valid open fixture, replace the first knot's width with the JSON number `12e4294967296`. Pinned Godot `JSON.parse` returned OK and decoded it as `12.0`. `RoadSourceDocument.parse_json` accepted the source and serialized the width as `12.0`, passing both finiteness and the [1, 100] guard at `:1245–1253`. The same happened for `12e18446744073709551616` and `12e-4294967296`. Bank tokens `1e2147483648` and `1e4294967296` became `0.0` and `1.0`. These tokens are grammatically valid. Their decoded values are wrong by orders of magnitude because the engine's exponent handling wraps. Decoded-value finiteness alone cannot catch this. Bound or safely decode the numeric exponent before handing the token to Godot, with an explicit refusal for values outside supported conversion limits. Add an end-to-end width or vector regression for an exponent that wraps to a plausible value, plus an ordinary signed-exponent positive control. The existing conversion and grammar tests (`tools/road_source_lab/road_source_checks.gd:722–789,932–1089`) miss this case.
