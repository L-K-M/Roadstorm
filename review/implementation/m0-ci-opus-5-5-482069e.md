## Implementation defects (ranked)

### F1 (important, certain): the failure-log printer is deleted but still called

- **Where:** the diff removes the definition of `ci_print_export_failure_log` (base `ci.sh` ~1748-1759). The candidate still calls it at `tools/ci/ci.sh:1961`, `:1966` and `:1973`. `git grep` finds no definition anywhere in the candidate tree.
- **Effect:** on every engine export failure (nonzero exit, engine error lines, or no output), `sh`/`dash` prints `ci_print_export_failure_log: not found` (bash: `command not found`) and goes on. The full engine log is **no longer printed**. The verdict is still `fail`, because `ci_report` and `return` follow the call.
- **Why it matters:** this undoes the fix for hosted run 45921573623, where Godot's multi-line, indented configuration errors were hidden. Both `README.md:117` ("On failure the full captured engine log is printed") and the workflow comment at `ci.yml:422-425` still claim the log is printed.
- **Why tests missed it:** the suite reaches this path. The zero-write concurrent attempt hits `ci.sh:1973`, but `run_tests.sh:2418` only greps for `export produced no output`, so 216/216 passed anyway.
- **Fix:** restore the function, and add a test that asserts a unique second-line marker from a failing engine log appears in the output.

### F2 (important, high confidence; hosted failure predicted, not observed): silent lock timeout on Linux

- **Where:** `ci.sh:1891-1904` delegates waiting to `flock -x -w N` or `lockf -k -t N` and returns the tool's exit status as is. `ci.sh` prints no message of its own on timeout, and the report gets no verdict line. The strings `held by another process` and `already locked` appear nowhere in `ci.sh` or `common.sh`.
- **The two tools differ:**
  - macOS `lockf(1)` prints `lockf: <file>: already locked` and exits 75.
  - util-linux `flock(1)` is **silent** on a `-w` timeout unless `--verbose` is given, and exits with the conflict code 1. ubuntu-latest has `flock`; Debian/Ubuntu ship no `lockf(1)`.
- **Consequence for hosted CI:** the case "a foreign lock FILE is preserved and a live owner blocks others" (`run_tests.sh:2582`) needs one of those two strings. On the `export-preparation` job (`ubuntu-latest`, `ci.yml:231`), that case should evaluate to `no`, `run_tests.sh` should exit 1, and the new step (`ci.yml:345-349`) should fail with `tools/ci self-test failed`. The local 216/216 run passed only because macOS uses `lockf`, which prints the message.
- **Product defect, separate from the test:** on Linux, a destination held by a live export makes a second export fail closed with exit 1, no reason, and no `export result=` line in its report. On macOS the exit code is 75, which `ci.sh` does not document.
- **Fix:** have `ci.sh` print its own message and write a `ci_report "export result=fail reason=lock-timeout …"` line. Normalise the exit code, either with `flock -E <code>` or by mapping 75. Make the test assert ci.sh's own message, not the tool's.

### F3 (important, mechanism certain from code; not executed): the lock outlives its owner

- **Where:** `common.sh:131-141`, plus `common.sh:84-101` for `ci_run_bounded`.
- **Mechanism:** `ci_run_godot` starts its watchdog as `( sleep "$_timeout"; kill …; sleep 3; kill … ) &` and later does `kill "$_watch"`. That kills the subshell but **orphans its running `sleep`**.
  - On this path the inner `ci.sh` runs as the command of `flock`/`lockf`, so every child inherits the lock descriptors.
  - util-linux `flock` passes the lock fd to the command by default; that is why it has the `-o/--close` option. FreeBSD/macOS `lockf` likewise forks and execs without, as far as I know, setting close-on-exec.
  - So the orphaned `sleep 300` from the import run and from the export run, plus the 30 s `sleep` from the `--version` probe, keep the destination locks held for up to `CI_TIMEOUT_DEFAULT` (300 s by default) after the export has finished or died.
- **Effects:**
  - The README's statement that "the kernel releases the lock when its owner exits … a stale lock file does not block a later export" (`README.md:117`) is not true for this process tree.
  - Re-exporting the same destination right after an export (once the outputs are moved away) waits about 5 minutes.
  - With `--timeout 1200` and the default `CI_EXPORT_LOCK_WAIT=900`, or with any `CI_EXPORT_LOCK_WAIT` below the remaining watchdog sleep, the re-export **fails closed although no export is active**. That is the stale-lock blockage this change set out to rule out.
  - The self-test cases "stale persistent lock files do not block a later export", "the zero-write attempt fails and the blocked attempt delivers…" and "stale persistent lock files are inert after SIGTERM" should still pass, but only after waits of up to about 300 s each. They are slow, and they do not prove what their names claim.
  - The hosted Build step is not affected: the three presets use disjoint destinations.
- **Not verified:**
  - Whether macOS `lockf` opens with `O_CLOEXEC`. If it does, the macOS path is immune, but Linux `flock` is not.
  - Any actual timing.
- **Reproduction (not run):** export once, `rm` the outputs, then immediately run the same export with `CI_EXPORT_LOCK_WAIT=5`. Expect a lock-timeout failure. Check `lsof <dest>.ci-lock` for a `sleep` process.
- **Fix:** have the watchdog `exec` a single process, or kill the whole watchdog process group. Alternatively, run the locked worker with `flock -o` on Linux; there is no `lockf` equivalent, so the fds would have to be closed in the watchdog.

### F4 (medium): the worker is re-executed through `$0`

- **Where:** `ci.sh:1890` builds the worker command from `$(_shq "$0")`, and `lockf`/`flock` run it with `execvp`. `CI_TOOLS_DIR` is already absolute and is not used here.
- **Counterexamples:**
  - `cd tools/ci && sh ci.sh export --export "Linux x86-64" --out /tmp/x`: `$0` is `ci.sh`, which has no slash, so `execvp` searches `PATH`, not the current directory. The worker is then either not found, or a different `ci.sh` on `PATH` runs.
  - `sh tools/ci/ci.sh …` from a tree without the exec bit (a zip download, or `core.fileMode=false`) fails with `Permission denied` (126).
  - A run started with `bash ci.sh` silently switches to `/bin/sh` for the worker.
- **What still works:** the workflow and the self-test both pass absolute, executable paths, so CI is not affected.
- **Fix:** run `sh "$CI_TOOLS_DIR/ci.sh"`.

### F5 (medium-low): global options are not forwarded to the locked worker

The inner process re-parses only `--project/--godot/--out/--source-sha`.

- `--strict-warnings`: `ci.sh:1883` exports `CI_STRICT_WARNINGS`, but `ci.sh:53` unconditionally resets it to `0` after `common.sh` has read it. As a result, `ci.sh --strict-warnings export --export …` no longer fails on unexpected warnings from the headless import that `ci_prepare_copy` runs (`common.sh:713`). Before this change it did, in the same process.
- `--in-place` and `--reuse-copy` are dropped silently.
- `--timeout` survives only through the exported `CI_TIMEOUT_DEFAULT`.
- **Fix:** forward these options explicitly.

### F6 (low-medium, workflow behaviour): lock files land in the package artifact

The persistent lock files sit next to each destination under `build/`. "Upload built packages" (`ci.yml:448-455`, `path: build/`) uploads them too. Each artifact therefore gains six zero-byte files, for example `Linux x86-64.ci-lock`, `Linux x86-64.pck.ci-lock`, and `macOS Apple Silicon.pck.ci-lock` for a sidecar that never exists. These are not package files, but anything consuming the artifact sees them. The fix is to exclude `*.ci-lock` from the upload, or to put the locks somewhere else.

### F7 (low): a signalled outer process leaves a live worker

The SIGTERM case (`run_tests.sh:2656-2660`) sends SIGTERM to `ROADSTORM_CI_LOCK_OWNER`, which is the **outer** `ci.sh`, and that process holds no lock. The lock tool and the inner worker keep running: the outer exits 143 while the worker can go on to write the package and append `export result=pass` to the same report.

The test passes because its shim writes nothing. It shows that the lock is eventually released by an orphan, not that "SIGTERM releases the advisory lock". A real Ctrl-C reaches the whole process group, so this only matters when a single PID is killed. Even so, a report can receive a PASS after the caller has already seen a failure.

### F8 (low, pathological input): a newline in `--out` breaks the lock list

`ci.sh:1860-1901` passes lock paths as newline-separated text and picks them with `head -n1`/`tail -n1`. With `--out "$D/a<NL>b"`, the sorted lines are `$D/a`, `$D/a`, `b.ci-lock` and `b.pck.ci-lock`. The tool then locks, and if necessary creates, the empty file `$D/a` plus `./b.pck.ci-lock` relative to the current directory. The main destination's lock is never taken. The fix is to refuse control characters in `--out`, or to keep the two paths in separate variables.

## Advisory-lock limitations under a hostile pathname swap (not implementation defects)

- **Check-then-open race:** there is a gap between the `-L`/`-e` precheck (`ci.sh:1865-1877`) and the `O_CREAT` open by `flock`/`lockf`. A symlink swapped in during that window is followed. A dangling link makes the tool create an empty file at the link's target, though it never writes or truncates existing bytes.
- **Replaced lock file:** unlinking or replacing a `.ci-lock` during a run lets a second invocation lock a different inode and run concurrently. `README.md:117` documents this.
- **Unlocked writers:** any process that does not use the lock can still create the destination between the locked existence check and Godot's write.
- **Network filesystems:** `flock`/`O_EXLOCK` semantics on network filesystems are unverified. That includes the SMB-mounted `/Volumes/PaseoData/TrueNAS` that holds this checkout. Local self-tests run under `TMPDIR`, so they never exercise it.

## Answers to the primary questions

- **Do the locks exclude overlapping main/sidecar exports?** Yes, for cooperating `ci.sh` processes on one host and a local filesystem. Locks are taken on both `<out>.ci-lock` and `<pck>.ci-lock` in a fixed order, so `game.x86_64` vs `game.exe` vs `game.pck` overlaps serialise. Case-insensitive aliases and symlinked-directory aliases resolve to the same inode. Exclusion is actually stronger than intended, because of F3.
- **Are pre-existing files, directories, symlinks and outputs preserved?** Yes in the code paths I read:
  - Output and sidecar are refused under the lock.
  - Lock files are opened read-only and never truncated or unlinked.
  - A symlink or non-regular file at the lock path is refused.
  - The caveats are the swap window above and F8.
- **Is stale-lock blockage avoided?** No; see F3.
- **Is the evidence bound to the source revision and the attempt?** Mostly:
  - The report and the inventory file share a mktemp-derived `CI_ATTEMPT_ID`. The inventory name carries a 12-character SHA tag, and the failure reason is kept in `logs/export-<slug>-<attempt>-inventory-failure.log`.
  - The binding lives in filenames only; the attempt id is not written inside the report.
  - `ci_init_report` adopts any `ROADSTORM_CI_REPORT` it finds in the environment (`common.sh:1020`), so a leaked variable redirects evidence and leaves `CI_ATTEMPT_ID` empty.
  - `mv` at `common.sh:1041` would overwrite on an id collision, which is negligible in practice.
  - Attempt-boundary evidence is weakened by F7.
- **Does hosted CI run the template-dependent negative tests, and fail if they skip?** By design, yes:
  - The step needs the `PASS` line.
  - It fails on the two template/engine skip notes.
  - It checks 21 case labels ending in `-> yes`.
  - Its `set -euo pipefail` and its grep checks are correct.
  - However, per F2 the step should fail on Linux for a test-assertion reason, not because of a real regression.
  - It does not check the separate skip note "symlinks are unavailable" (polish).

## Optional polish

- `ROADSTORM_CI_LOCK_OWNER` names the outer shell, not the process that holds the lock. `ROADSTORM_CI_PID` is exported but nothing uses it.
- `__export-inner` can be called directly and bypasses the locks; gate it on a private token.
- BusyBox `flock` has no `-w`, so it fails closed with a usage message. Detect this and say so.
- `export-<slug>-N-*.log` names are only unique per process. Two concurrent same-preset exports that share `--out <CI dir>` overwrite each other's logs. They also `rm -rf` each other's live `project-copy` (`common.sh:625`). Both problems predate this change, but the README now advertises concurrent non-overlapping exports. The test avoids both by giving each run its own `--out` root, which deserves a mention in the README.
- The contract-suite interpreter versions now go only to the step summary and no longer appear in the job log.
